including its own landing page, whose prose carries the generation's

future drift fails verification instead of shipping silently.

## In-flight fixes (pipeline standard — caught in testing, fixed in
## the same motion, recorded here)

1. The first generation exposed 4.48M characters of repeated
   evidence links (page-level dataset unions duplicated per
   fragment). Evidence links were re-scoped to the fragment itself:
   its page's per-page JSON plus the dataset files named by the
   questions bound to it. File size 12.42 MB → 6.93 MB at the same
   information content.
2. Three seed-shape mismatches in the landing-div builder
   (observation `url` field, profile string fields, gap `solution`
   field) — fixed in the builder, no data changed.
3. The new landing div's opening tag carried a `data-page`
   attribute no other page div carries; build-routes' extractor
   rejected the shell (206 divs vs 207 registry). Normalized.
4. The new pageMeta entries were first written with head-data field
   names (t/d/c); build-routes rejected them (no `canonical`).
   Corrected to pageMeta fields (name/svc/canonical/desc) in shell
   + main.js; the surfaces script was corrected for the record.
5. verify's pre-deploy run caught `pages.json`'s registry `count`
   field still reading 206 — set to 207.
6. The pass-B count sync's data-txt step was written against the
   wrong file format (the llms.txt list); investigation showed the
   data txt uses dated prose entries and that the local copy had
   drifted behind the pushed B1 state. Healed from the pushed copy
   and appended the B2 entry in the file's own style.
